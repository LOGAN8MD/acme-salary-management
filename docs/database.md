# Database setup and guarantees

Task 3 implements PostgreSQL storage with Prisma 7.10.0. The generated client is ignored by Git and regenerated by `npm ci` (postinstall) or `npm run db:generate`.

## Local review

```sh
npm ci
cp .env.example .env  # only when .env does not already exist
npm run db:local
```

Leave the database process running. In a second terminal:

```sh
npm run db:migrate
npm run db:status
npm run test:db
```

The local helper binds to loopback port 55432, uses development-only credentials from `.env.example`, and stores data in ignored `.local/postgres`. Ctrl+C stops PostgreSQL without removing its data. Restart with the same command. No migration or seeding runs automatically when the database starts.

The helper uses `embedded-postgres` as development tooling (its wrapper is beta; the bundled database is PostgreSQL 18.4). Production should use managed PostgreSQL with its own credentials. An existing PostgreSQL instance can be used instead: create an empty database, configure `DATABASE_URL`, and run `db:migrate`. Never use the example credentials for a remote deployment.

`test:db` creates a separate temporary cluster on an available port, applies both committed migrations, repeats deployment to verify idempotency, runs integration tests, and shuts down/removes that temporary cluster. It ignores your configured database URL. The test file refuses execution unless the runner marks the connection as disposable. Run as an ordinary user; the helper does not create operating-system users or support running PostgreSQL as root.

## Tables and guarantees

- `hr_users`: unique normalized email and password hash.
- `sessions`: unique opaque-token hash, nullable user for anonymous CSRF bootstrap, expiry index and expiry-after-creation check.
- `employees`: unique employee code/email, country format and nonempty profile fields; indexes on country, department, and level.
- `current_salaries`: at most one row per employee; exact `NUMERIC(18,2)` amount, supported currency, positive version, currency index.
- `salary_changes`: initial/revision kind, amounts, reason, actor, version and timestamp; unique employee/version pair and ordered employee-history index.

Foreign keys restrict deletion of referenced records. Database checks reject nonpositive or nonfinite salaries, unsupported currencies, fractional stored JPY values, invalid revision/initial combinations, unchanged revisions, and missing/invalid reasons. SQL checks are kept in a separate migration because Prisma's schema language does not represent them.

PostgreSQL's `NUMERIC(18,2)` rounds excess fractional digits before CHECK evaluation. The Task 9 API rejects excessive precision before writing. Tests verify exact retention of supported two-decimal values, including values beyond JavaScript safe-integer precision. Backend money logic does not convert amounts to JavaScript numbers.

The database enforces **at most one** current salary per employee, not existence of a salary for every employee. Task 4 creates employees, salaries, and coherent history together in one seed transaction and checks consistency before accepting reruns. Task 9 enforces fixed currency, expected-version concurrency, matching current/history amounts, and append-only revisions in one transaction. These are not database triggers. See [seed behavior](seeding.md).

## Migration workflow

`202609280001_initial_schema` creates tables, keys, and indexes. `202609280002_data_constraints` adds checks. Apply committed migrations using `db:migrate`; do not use `db push`, which does not reproduce custom checks. Never rewrite an applied migration. Future changes need a new reviewed SQL migration and tests. UUID defaults are generated by Prisma; raw SQL inserts must supply IDs. `updated_at` is maintained by Prisma writes, not by a database trigger.

The API now has a reusable client factory in `apps/api/src/db/client.ts`, exercised by real database tests. Task 5 wires the database into HTTP authentication and closes the client at shutdown. Readiness and employee/salary/report endpoints remain pending.

## Dependency decisions

Prisma CLI/client/adapter are pinned to the same stable release. The latest npm tag was a release candidate when checked. `deepmerge-ts` 8.0.2 and `mysql2` 3.24.4 are overridden to address advisories in Prisma's dependency tree; migration generation, application, and tests are rerun against those versions. Revisit overrides when upstream resolves its dependency ranges.

Prisma setup follows its [official v7 migration guide](https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7): URL configuration lives in `prisma.config.ts`, the generated client has an explicit output path, and PostgreSQL uses the driver adapter.
